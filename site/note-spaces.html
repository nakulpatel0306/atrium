A space, not a chat thread.

Most of the time I spent prompting AI wasn't spent on the question. It was spent re-explaining the situation. Atrium's spaces exist to stop that.

NP Nakul Patel / November 6, 2026 / 4 min read

Here's a loop I ran for months. Open a chat window. Paste in the relevant file. Explain the project in a paragraph. Ask the actual question. Copy the answer back out. Next day, new chat, do it all again.

Chat is a great interface for a one-off question. It's a poor one for ongoing work, because ongoing work lives in context, and a fresh conversation starts with none. Atrium is the tool I built for the ongoing kind, and the piece that does the most work is the simplest: the space.

The re-paste loop

A model only knows what's in its context window: the text it can see at once, in this conversation. Nothing carries over unless you put it there. So every new chat costs a setup ritual:

  • Copy and paste the files that matter, and hope you picked the right ones.
  • Explain again what the project is, what you already tried, and how you like things done.
  • Carry the result out by hand: copy the code into your editor, the text into Messages, the file into a folder.
  • Lose it when the thread scrolls away. Finding last week's answer means searching old chats.

To be fair, chat tools have been adding memory and projects to soften this, and they help. But the shape is the same: you're the one moving context in and results out, and the model can't touch anything on its own.

What a space holds

In plain terms

A space is one ongoing area of my life or work: a code project, a job search, my investing, my texts. Every task belongs to one, and every task in it starts with what the space knows.

A space keeps five things, so I don't have to:

  • GoalOne line saying what this space is for.

    “Keep my job search organized.” It goes into every task's instructions, so the agent always knows why it's doing the thing.

  • Folder or repoWhere the work lives.

    A code space points at a repo on my Mac, or at a GitHub repo that Atrium clones the first time a task needs it. Any other space gets its own folder under ~/Atrium, where I can open it in Finder. Files a task leaves there are still there for the next task.

  • Agent and reviewerWho does the work, and who checks it.

    Each task can name an agent, or leave it on Auto. A code space can also name a second agent that reviews every finished change before it reaches me.

  • PrivateWhose eyes the data reaches.

    A private space's work only ever goes to Claude; Codex and Gemini are refused there. That's enforced by the engine, not by me remembering to choose carefully.

  • HistoryEverything that happened, in one place.

    Every run keeps its full transcript, what it changed and when. The space's activity feed says what was asked, what ran, what I approved or sent back, and who decided.

What the agent actually receives

I want to be precise here, because “it remembers everything” is the kind of claim AI tools make loosely. Atrium does not feed old conversations back into the model. What a task's agent gets is short:

src/engine/runner.ts · buildPrompt 
function buildPrompt(task: Task, space: Space): string {
  const parts = [`Task: ${task.title}`];
  if (task.detail.trim()) parts.push(task.detail.trim());
  if (space.goal.trim()) parts.push(`Space goal: ${space.goal.trim()}`);
  return parts.join("\n\n");
}

The title, any detail I added, and the space's goal. Plus a few fixed rules: work in this folder, never touch secrets, say honestly whether you finished. Then the agent starts inside the space's folder or repo, so the actual files are right there to read.

That's deliberate. Files are exact and always current. Old conversations are long, full of false starts and things that have since changed. A model handed a repo and a one-line task does better than one handed a repo plus a week of chat about it. It's the same idea I use when I brief agents myself: give them files, not history.

The history is for me, not the model. When I want to know why something is the way it is, it's in the space's activity and transcripts, not lost in a scrolled-away chat.

Results that land somewhere

The other half of the chat loop is getting results back out. In a space, there's nothing to copy. A code task's changes are committed to a branch of their own in the repo. Files a general task makes are saved in the space's folder, and its review card lists exactly which files it created, changed or deleted. A text an agent drafts becomes a card with a Send button.

All of it waits in one list, Needs you, until I approve it. Nothing gets sent or kept until I say yes.

A chat answer is a suggestion I have to carry somewhere. A space's result is already where it belongs, waiting for a yes.

When chat is still the right tool

I still open a chat window for quick questions: explain this error, what's the syntax for that. Setting up a space for a single question would be silly.

The line I draw is whether the work has a tomorrow. If I'll come back to it, if it touches files, or if the result needs to end up somewhere other than my clipboard, it gets a space. Setting one up takes a sentence: I describe what I want in Atrium's Ask box, and an agent sets up the space with a name, a goal and its first tasks.
