Testing code that agents write.

Agents write most of Atrium's code and most of its tests. That makes the tests both more important and less trustworthy, so a few rules decide what counts.

NP Nakul Patel / November 7, 2026 / 6 min read
On this page
  1. Nine groups, zero failures
  2. Agents that aren't agents
  3. A fresh home for every test
  4. The flaky test that was a race
  5. A fix only counts if its test fails without it

Here's the uncomfortable part of having agents build software: the agent that writes the code usually writes the tests too. Its tests check what it thought to check. If it misunderstood something, the code and the test agree with each other and both are wrong.

In Plan 15, the two important bugs the reviewer found had passed every test. So I don't treat a green test run as proof. I treat it as one piece of evidence, and I've built a few habits around making that evidence worth more.

Nine groups, zero failures

Atrium's tests run with bun test, in nine groups, each run on its own:

  • enginerunner, git, sandbox, money
  • serverHTTP routes
  • dashboardweb UI
  • e2eend to end
  • tuiterminal app
  • macMac app
  • copyUI wording
  • cli
  • main

A plan isn't done until every group reports zero failures and bunx tsc --noEmit, the TypeScript type check, is clean. When Plan 15 merged today, that was 1,881 tests across the nine groups, all passing.

The copy group is the odd one out, and one of my favorites. It pulls every user-facing string out of the code and checks it against the copy rules written down in the repo: buttons in sentence case, no “Error:” prefixes, errors that end with a full stop, a real ellipsis instead of three dots. An agent that labels a button “Save Changes” fails a test, not just my taste.

Agents that aren't agents

Atrium's whole job is running Claude, Codex and Gemini. Tests can't call the real ones: that would be slow, cost money, depend on the network and do unpredictable things.

In plain terms

A fake is a small stand-in program that behaves like the real one from the outside: same arguments, same output format, same exit codes. It just doesn't do the real work.

The repo has a fake for every outside program Atrium starts, in tests/fixtures. fake-claude.ts prints the same stream of JSON lines Claude Code 2.1.x emits. fake-codex.ts and fake-agy.ts do the same for Codex and for agy, the CLI Atrium runs Gemini through. There are fakes for the GitHub CLI (its “repos” are bare git repos in a temp folder), for open, for osascript (which logs its arguments and never scripts any app), and for security, where a JSON file plays the Keychain.

tests/fixtures/fake-claude.ts, first lines 
#!/usr/bin/env bun
// Stands in for the `claude` CLI; mirrors the stream-json lines Claude Code 2.1.x emits.
const mode = process.env.FAKE_CLAUDE_MODE ?? "ok";

The mode picks a behavior: ok, crash, logged_out, rate_limited, slow, write_files, sandbox_unavailable and more. So a test of “what does Atrium say when Claude hits its usage limit” runs in milliseconds and never touches my real account.

This only works because the engine was built for it. The path to each CLI comes from config, so a test can point it at a fake. That was in the project rules from the first day.

A fresh home for every test

Atrium keeps its database, transcripts and settings in a data folder. The folder comes from the ATRIUM_HOME environment variable when it's set, and every test sets it to a brand new temporary folder:

tests/helpers.ts, trimmed 
export function tempHome(): { home: string; cleanup(): void } {
  const home = mkdtempSync(join(tmpdir(), "atrium-home-"));
  process.env.ATRIUM_HOME = home;
  // Space folders stay inside the temp home, never the real ~/Atrium.
  process.env.ATRIUM_FILES_HOME = join(home, "files");
  // Tests never launch real apps.
  process.env.ATRIUM_OPEN_BIN ??= join(import.meta.dir, "fixtures", "fake-open.ts");
  // Tests never script Messages or Contacts.
  process.env.ATRIUM_OSASCRIPT_BIN ??= join(import.meta.dir, "fixtures", "fake-osascript.ts");
  // … cleanup() removes the folder
}

That buys two things. Tests can't see each other's leftovers, so the order they run in doesn't matter. And my real Atrium, with my real texts and portfolio, is never in reach. A test that tried to send a message would reach a fake that writes to a log.

Pin the clock, too

Time is the other shared thing tests forget about. A money test failed today on main, with no code change. It pinned the engine's clock to November 5, but the summary it checked read the real wall clock with a two-day window. On November 7 the window closed and the test broke. The fix was to pin the system time for the length of the test. Any test that reads “now” should decide what now is.

The flaky test that was a race

During the Plan 15 review, one terminal-app test failed once under load and then passed three times on its own. The easy call is to label it flaky and move on.

In plain terms

A flaky test passes and fails on the same code. A race is a bug where the result depends on which of two things happens first. Races make flaky tests, because the order changes with how busy the machine is.

Here's what was going on. When I open a running task, the terminal app shows the agent's live output. That output reaches it two ways: a catch-up request over HTTP for the transcript so far, and a live stream over a WebSocket, a connection that stays open so the engine can push each new line as it happens.

The engine writes each line to the transcript file first, then sends it on the socket. Two connections means no promise about which arrives first. If the transcript response, which already held the newest line, got to the app before that line's socket message did, the app had finished loading. Then the late message arrived and was added again. The line showed twice.

The fix numbers each run's lines. Every live message carries a seq, a count that goes up by one per line. The transcript route reads the current count and the file in one synchronous step, so no line can be appended between the two, and sends the count in an X-Atrium-Output-Seq header. The app then skips any line numbered at or below that count, whichever connection brings it.

src/tui/client.ts 
// A line the loaded transcript already has; it can arrive after the transcript did, on the other connection.
const had = seededSeq.get(msg.runId);
if (had !== undefined && msg.seq !== undefined && msg.seq <= had) return;

Engines that don't send the header still work: the app falls back to the old way of matching lines by their text.

Not every red run is a bug, to be fair. Earlier in the same fix wave, a full run failed a scattered handful of unrelated tests that each took one to six minutes. That was the machine stalling, not the code, and the clean run straight after had normal timings. The difference is evidence. A stalled machine shows up in the timings. A race shows up in the logic, once you look.

A fix only counts if its test fails without it

This is the rule I'd keep if I could only keep one. A test that passes before and after a fix proves nothing about the fix.

The race was tricky to test because it depends on timing. So the new tests don't wait for luck. They drive both orders on purpose: one holds the transcript request back so the live line arrives first, the other sends the line after the transcript has loaded. The “after” test fails on the old client. That's what makes it a real test of the fix, and not just a test that happens to be green.

The second reviewer caught the opposite case in the same plan. The fix wave's test for the money summary checked that transaction rows were gone, but its sample data had no notable charge, so it couldn't have failed. The fix was half-done and the test was green. The new test first checks that its sample data really has a notable charge, then that the summary's list of them is empty.

The Money review yesterday did it best. It left 12 small tests in its scratchpad, one per finding plus a control. Eleven failed on the branch as it was, and the control passed. Each finding came with its own proof.

  1. Fakes for everything outside the process.

    No real agents, no real apps, no real Keychain. The engine takes every binary path from config so tests can swap them.

  2. A temp home and a pinned clock.

    Nothing shared between tests: not files, not settings, not “now”.

  3. “Flaky” is a hypothesis, not a verdict.

    Look at the timings and the logic before deciding it's the machine.

  4. Red first.

    Every fix comes with a test that fails without it. If you can't make it fail, you haven't tested the fix.
