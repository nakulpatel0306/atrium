Why one agent isn't enough.

A single agent doing everything drifts and grades its own work. Here's the pipeline I build Atrium with instead, and the three rules that hold it together.

NP Nakul Patel / November 5, 2026 / 5 min read

This week I started building Atrium, a command center for the AI agents on my Mac. I type what I want in plain words, an agent (Claude, Codex or Gemini) does the work in a sandbox, and the finished work waits in a list called Needs you. Nothing gets sent or kept until I say yes. I call that rule draft and wait.

Under the hood it's a bun and TypeScript engine running on the Mac. Most of its code is being written by agents too, working from plans I write with them. This note is about how that's set up, and why it isn't one agent doing everything.

Two reasons one agent drifts

A single agent doing a whole feature gets worse the longer it runs. There are two reasons, and they're worth separating.

It runs out of room

A model only knows what's in its context window: all the text it can see at once. That includes my instructions, every file it opened, the output of every command it ran and its own earlier replies.

The window is big, but a real feature fills it. Long before it's full, the requirement I wrote at the start is competing with pages of test output. When it does fill, the tool summarizes older parts to make room, and summaries lose the exact details. I wrote more about this in Tokens, explained simply.

It agrees with itself

Ask a model to review code it just wrote and it mostly agrees with itself. It remembers why it made each choice, so each choice feels justified. People have the same problem proofreading their own writing: you read what you meant, not what's on the page.

Software teams solved both problems a long time ago by splitting the work into roles. One person writes the spec, one builds, someone else reviews. I do the same with agents. Each role gets its own, smaller context holding only what that role needs.

In plain terms

A subagent is a fresh agent session that a main session starts with a written brief. It begins with an empty context, sees only the brief and whatever it reads, does its job on its own, and sends back a short report. Then its context is thrown away.

The pipeline

Every plan for Atrium goes through the same seven steps. None of it is new. It's the way a careful team works, with agents filling most of the seats.

A written plan

Each piece of work starts as a numbered plan in the repo's docs/plans folder. It says what the feature is, which files it touches, what's out of scope, and which test groups have to pass. I write it in conversation with the strongest model I have, and I read every line. The plan is the contract: the builder is judged against it, and the reviewer checks the code against it.

One builder, in its own worktree

In plain terms

A git worktree is a second working copy of the same repository, checked out in its own folder on its own branch. Changes there don't touch the files in my main checkout.

The builder agent gets one worktree and one branch, in a folder next to the repo like atrium-wt-tui. It can commit to that branch as often as it likes. It can't merge, can't push and never touches main. My main checkout is where the installed engine runs, so keeping builders out of it means the Atrium I use every day keeps working while they build. If a run goes badly, I delete the folder and nothing is lost.

It's one builder per plan. Two builders on the same plan edit the same files, and untangling their work is a job I'd rather not have. Separate plans can run side by side in their own worktrees when they touch different files. When they share files, the second one waits for the first to merge.

An independent reviewer

When the builder says it's done, a fresh agent reviews the branch. It reads what's on disk: the plan, the diff, the tests and the builder's written report. It never sees the builder's conversation, so it never watched the builder talk itself into a choice.

That matters because of anchoring: the first explanation you hear shapes everything you look for afterwards. A reviewer that had followed the builder's reasoning would tend to check the edge cases the builder thought of, the way the builder thought of them. A fresh one has to form its own view from the code. Its findings come back sorted as critical, important or minor.

One fix wave, then a scoped re-review

All the findings go to a fix agent in one batch. One wave, not a back-and-forth. Every round trip costs a new brief and a rebuilt context, and fixes handled one at a time have a way of undoing each other.

Then a second review looks at only the fix diff, meaning just the changes the fix wave made, checked against the list of findings. Re-reviewing the whole branch would cost nearly as much as the first review and mostly re-confirm what was already checked.

Tests, then a human

Then every test group runs, and the bar is zero failures. Not “zero except the flaky one”. A flaky test is one that sometimes passes and sometimes fails on the same code, and in my experience a lot of them turn out to be real bugs.

Only then do I read the diff, try the feature and merge it myself.

Three rules that hold the whole way through

  1. Builders never merge or push.

    Agents write to a branch. A person moves code to main. That keeps exactly one place where a human has to look.

  2. No subagents spawning subagents.

    One level of delegation. A subagent that starts its own helpers multiplies the token bill, and its report back becomes a summary of summaries that nobody can check.

  3. Nothing touches live data.

    Agents work against temporary folders, seeded sample data and a separate copy of the engine on its own port. Never my real Atrium on port 7420, with my real texts and portfolio.

None of this is exotic. It's the separation of duties software teams already use: someone writes the spec, someone builds, someone else reviews, and someone accountable presses merge. Agents make each role cheap to fill. They don't make the roles unnecessary.
