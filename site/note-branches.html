A branch for every task.

When an agent works in one of my repos, it gets a branch of its own, it never lands on top of my uncommitted work, and an unfinished run is saved rather than lost.

NP Nakul Patel / November 5, 2026 / 5 min read

Atrium can point an agent at one of my code repos and ask it to change something. That's useful, and it's also the most obvious way for an agent to make a mess of my day.

Two things worry me. The agent's edits could get mixed up with mine. And a run that stops halfway, because it failed, hit a usage limit or the engine shut down, could leave half-edited files lying around in a repo I'm about to open.

Git already has the tools to prevent both. This note is about how Atrium uses them.

Two tools from git

In plain terms

A branch is a named line of commits. Work on one branch doesn't change another until someone merges them.

A worktree is a second working copy of the same repository, in its own folder, with its own branch checked out.

I use both, for different jobs. The agents that build Atrium itself each get a worktree, which I wrote about in Why one agent isn't enough. That keeps my main checkout, where the installed engine runs, untouched while they work.

Atrium's own repo tasks work differently. They use a branch in the repo I pointed the space at. While an agent works, that repo is switched to the task's branch, and when the run ends Atrium switches it back. That's simpler, but it means the rules about when it's safe to switch matter a lot.

One branch per task

Every repo task gets a branch named atrium/<taskId>, like atrium/tsk_4f9a2c. The name says who made it and which task it belongs to, so I can tell an agent's branch from mine at a glance in lazygit.

Before creating it, Atrium checks that the name is a valid branch name with git check-ref-format, and it refuses outright to work on main or master. The agent's instructions say the same thing in words: work only on the current branch, don't switch or create branches, never push or merge. But the engine doesn't rely on the agent listening.

Never over your uncommitted work

This is the rule I care about most: Atrium never checks out over uncommitted changes of mine.

It's easy to get wrong, because git checkout is friendlier than you'd expect. If you have uncommitted edits that don't conflict with the branch you're switching to, git carries them along. That's handy for a person. For Atrium it would mean my half-finished work quietly ending up on the agent's branch, and then in the agent's commit.

So before it creates or switches to a task branch, the engine runs git status --porcelain. If anything at all is listed, it stops and tells me.

src/engine/git.ts · prepareBranch, trimmed 
// checkout carries non-conflicting uncommitted changes along, which would put the user's WIP on the agent branch.
const status = await git(path, ["status", "--porcelain"]);
if (status.out.trim() !== "") throw new Error(`You have uncommitted changes in ${path}`);
// A retry after a send-back reuses the existing branch. Plain checkout (never --force)
// fails rather than overwrite local changes.
const exists = await git(path, ["rev-parse", "--verify", "--quiet", `refs/heads/${branch}`]);
const res = await git(path, exists.code === 0 ? ["checkout", branch] : ["checkout", "-b", branch]);

The task goes to blocked with that message, and it runs once I've committed or stashed. Two more checks sit next to this one:

  • If the repo is already on some atrium/ branch, Atrium won't branch from it. Starting from a leftover agent branch would stack unreviewed work on top of unreviewed work.
  • If the repo is dirty and on this task's own branch, those changes are what a killed run left behind, not mine. The task blocks with a message that says exactly that, and where to commit or stash them.

The agent edits, the engine commits

Agents in Atrium don't run git commit. Their instructions say to leave changes uncommitted, and in a repo the only git commands Claude is allowed are git status, git diff and git log, next to reading and editing files, bun test and bunx tsc. When the run ends, the engine commits whatever the agent left.

Moving the commit to the engine sounds like a small thing. It's where most of the safety lives, because an agent can write files inside the repo, including git's own settings. So the engine's commit step is careful:

  • Hooks are off. Every git call runs with core.hooksPath=/dev/null, so a hook the agent planted never runs with the engine's permissions.
  • Settings are fingerprinted. Before the run, Atrium takes a fingerprint of the repo's git config, hooks and attributes. If it changed, the engine refuses to commit or even switch branches, and tells me to check them.
  • No .env files, ever. Any path that looks like a .env file blocks the commit, including the old name in a rename, so .env → notes.txt can't sneak a secret out under a new name.
  • My identity, my signing. Commits use my configured git identity. Signing is left to my own git config rather than forced, so repos without signing set up still work.

When a run doesn't finish

Runs end early. The agent fails, the account hits its usage limit, or I quit the engine. Before today, that left uncommitted edits sitting on the task branch, and the next task in that repo would refuse to start because the tree wasn't clean.

Now the engine commits them anyway, as a WIP commit: a work-in-progress commit with a message that says so.

src/engine/runner.ts 
const message = stopped ? `WIP (stopped): ${task.title}` : task.title;

Then the repo switches back to the branch I was on, but only if the tree is clean. If something is still uncommitted, Atrium leaves it alone and tells me, rather than carrying it onto my branch.

The task's reason line says where the work went: “Atrium saved the agent's unfinished edits as a WIP commit on atrium/tsk_4f9a2c; retry to carry on from there.” And that's exactly what Retry does. The branch already exists, so it's checked out instead of created, and the agent starts with the earlier edits in place. The summary in Needs you counts from where the first run started, so it shows all the work on the branch, not just the last run's.

Fixes are a little different

A fix is a follow-up task that adds to a branch I'm reviewing. If a fix doesn't finish, its half-done edits shouldn't land on the branch I'm about to decide on. So they go on a branch of their own, numbered if the name is taken: atrium/tsk_8k2m1q, then atrium/tsk_8k2m1q-2.

The same goes for a fix that commits just after I've already approved or rejected. Its commit is moved to its own branch, and the reviewed branch is put back with a compare-and-swap: git only moves it if it still points where the engine expects, so nothing anyone else put there is lost.

Nothing leaves the Mac

The last line of every repo result is the same: “Branch atrium/tsk_4f9a2c is on your machine. Push it when you're ready.”

Atrium never pushes as me. Agents can't push: they get no GitHub CLI, no SSH and none of my GitHub tokens. The engine only pushes or creates repos after I've said yes to that specific thing. A branch is a draft, and drafts wait for me. Same rule as everything else in Atrium.
