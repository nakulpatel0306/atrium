Stopping a running agent safely.

A Stop button sounds like the easiest feature in the app. Mine reported success when nothing had stopped, and fixing it meant getting processes, signals and honest answers right.

NP Nakul Patel / November 7, 2026 / 6 min read
On this page

  4. Telling the truth about what happened
  5. Two edges the reviewers found

Plan 15 gave Atrium a Stop button: a two-step Stop… on a running task in the dashboard, and the . key in the terminal app. I wrote about the rest of that plan in Plan 15, start to finish.

The first version passed its tests. Then the reviewer found that it said “stopped” when the task had already finished, and when the agent simply ignored the request. This note is about what stopping actually involves, and how the fixed version decides what to tell me.

Processes, signals and groups

A few words first, because the whole feature rests on them.

In plain terms

A process is a running program. Each one has a number, its pid.

A signal is a short message the operating system delivers to a process. SIGTERM politely asks it to exit, and a program can catch it, clean up, or ignore it. SIGKILL ends it at once. It can't be caught or ignored.

A process group is a set of processes that can be signalled together. A program and the commands it starts usually share one.

An agent is rarely one process. Claude Code runs shell commands, and those commands can start their own children, like a test runner or a dev server left running in the background. Stopping the agent but leaving its children alive isn't stopping it.

So Atrium starts every agent with detached: true. That puts the agent in a new session and a new process group of its own, with the agent as the group's leader. Its group number is its pid. Sending a signal to the negative of that number reaches the agent and everything it started, and nothing else.

The sequence

When I press Stop, the engine aborts that run. Bun, the runtime Atrium is built on, turns the abort into a SIGTERM to the agent's process. A well-behaved agent exits, and the engine's normal cleanup runs.

Not every agent is well-behaved. One that traps SIGTERM, or a child that holds the group open, would keep the run alive forever. That was the first half of the bug. So after a grace period the engine stops asking.

The escalation is a timer armed on the run's own abort signal:

src/engine/agents/process.ts 
// Bun sends SIGTERM to the main process on abort; one that ignores it (or a child holding the group open) would
// keep the run alive, so the group is killed after a grace period.
let escalate: ReturnType<typeof setTimeout> | undefined;
const onAbort = () => {
  escalate = setTimeout(() => {
    try {
      process.kill(-proc.pid, "SIGKILL");
    } catch {
      // ESRCH: everything already exited.
    }
  }, opts.abortGraceMs ?? ABORT_GRACE_MS);
};

The timer is cleared as soon as the agent exits. After that, every run ends the same way, stopped or not: the engine sends SIGTERM to the whole group, waits up to 300 ms, and sends SIGKILL to anything left. That sweep has been there since the first day of the project, because agents' background commands would otherwise outlive the run.

Never the wrong process

A line like process.kill(-pid, "SIGKILL") deserves suspicion, because the number matters enormously. If pid were 0, -0 is just 0, which means “my own process group”, and the engine would kill itself. If it were 1, -1 means “every process I'm allowed to signal”, which on a Mac is most of what I'm running.

So the re-review checked it specifically. The kill only runs after Bun.spawn has succeeded with detached: true, so proc.pid is always the run's own group leader. It can never be 0, 1 or the engine's own pid. The timer is only armed by that run's abort, and the listener is removed when the run ends. Every agent, Claude, Codex and Gemini, goes through this same function.

Telling the truth about what happened

The second half of the bug was the answer. The old route returned success whatever happened. Now stopTask waits for the run to settle, up to 10 seconds, and returns one of four outcomes. The HTTP route maps each to its own status code.

In plain terms

An HTTP status code is the three-digit number a server sends with every answer. 200 means it worked. 202 means accepted, but not finished yet. 409 means conflict: the request doesn't fit the current state of things.

  • 200 · StoppedThe run ended because I stopped it.

    The task goes to blocked, not failed or back in the queue, so it doesn't restart on its own. Its reason reads “You stopped this task.” plus where the edits went: a WIP commit on its branch in a repo, or “Retry to run it again.” Retry carries on from that commit, the same way it does after any unfinished run, which I covered in A branch for every task.

  • 409 · Finished firstThe agent had already answered.

    “It finished before it could be stopped, so its result stands.” The result goes to review as usual. Pretending it was stopped would throw away real work and lie about it.

  • 202 · Still winding downThe agent hasn't exited yet.

    The reply carries the task, still running. The clients say “the agent hasn't exited yet; Atrium marks it stopped when it does”, and it does.

  • 409 · Not runningThere's nothing to stop.

    Either the task isn't running, or the database says it is but the runner has no live run for it. That second message says to restart the engine if the task still shows as running.

The dashboard and the terminal app both word their message from the task's status in the reply, so they can't disagree about what happened.

Two edges the reviewers found

A stop that lands during the commit step

A run can fail on its own, or hit a usage limit, a moment before my stop arrives. Then the abort lands while the engine is committing, and the old code would relabel that failure as “stopped”. Now the engine notes whether the signal fired before the agent answered, and if the agent answered first, its own outcome stands.

Two stops at once

If the dashboard and the terminal app stop the same task together, both wait on the same run. The first answer used to clear the record that the stop was mine, so the second got 409 “finished first” for a task that was in fact stopped. The fix was one word:

src/engine/runner.ts · stopTask 
// `has`, not `delete`: a second stop of the same run waits on the same promise and must hear the same answer.
return stoppedByStop.has(taskId) ? "stopped" : "finished";

Testing an agent that won't stop

The test for the kill is a stand-in agent that refuses to die. It's a bash loop that traps SIGTERM and does nothing with it:

tests/engine/runner.test.ts, trimmed 
test("an agent that ignores SIGTERM is killed after the grace period", async () => {
  const running = runAgentProcess(["bash", "-c", `trap '' TERM; echo $$ > ${pidFile}; while true; do sleep 0.05; done`],
    { cwd: home.home, stdin: "", signal: controller.signal, abortGraceMs: 200, onLine() {} });
  // … wait for the pid file, then:
  controller.abort();
  const res = await running;
  expect("aborted" in res && res.aborted).toBe(true);
  expect(Date.now() - started).toBeLessThan(3000);
  expect(() => process.kill(pid, 0)).toThrow();
});

The last line is the one that matters. Signal 0 doesn't do anything to a process; it only checks that it exists. If that call throws, the stubborn agent is really gone.

Around it sit tests for every outcome above: the timeout and then the task ending stopped, finished first, a stop after a failure or a usage limit, stopping a review or a fix, Retry resuming from the WIP branch, the 409 and 202 codes, and a dashboard click-through that sends the stop.

A Stop button that sometimes lies is worse than no Stop button. Now it says what happened, even when the answer is “not yet”.
