Hand it off and walk away.

The point of an agent is that it works while I don't. That only happens if I can leave, so Atrium is built to run unattended and tell me what happened when I'm back.

NP Nakul Patel / November 6, 2026 / 4 min read

The way most people use AI today is synchronous. You type, you watch it stream, you read the answer, you type again. If the model goes off track, you're right there to stop it. That's fine for a question. For a task that takes twenty minutes, it means twenty minutes of watching a tab.

Atrium works the other way round. I describe the task, close the laptop or go do something else, and come back to results. This note is about what makes that safe and predictable: a queue, some rules about when work may run, and one place where finished work waits.

A queue, not a conversation

When I ask for something, Atrium turns it into a task: a title, maybe some detail, the space it belongs to and which agent should do it. The task goes into a queue and I'm done. I can add five more before the first one starts.

The engine runs on my Mac as a background service, and macOS restarts it if it ever crashes. When it's idle it does nothing at all: no polling loop asking “anything yet?” every second. It wakes when something happens, like a new task or an approval, plus one power check a minute.

By default it runs one task at a time, and never two in the same space, because two agents in one folder would trip over each other's files. Everything else waits its turn, and every waiting task says exactly why it's waiting.

What decides when a task runs

Each time the engine wakes, it walks the queue and asks a few questions about every task. A no to any of them means the task waits, with a plain sentence saying why.

Power

Each task is marked heavy or light. Heavy work, like a big code change with test runs, only starts when the Mac is plugged in. On battery it waits with “Waiting for power. Heavy work runs when your Mac is plugged in.” Light work, like drafting a text, runs anytime. A single task can be allowed on battery if I need it now.

The agent

The agent has to be installed and signed in, and allowed in this space (a private space only takes Claude). Claude runs on my subscription, and I don't want background work to eat the whole usage window before I sit down. So once half of Claude's five-hour window is used, Claude tasks wait: “Saving the rest of your Claude window for you.” “Run now” skips that wait for one task.

Usage limits

If an agent hits its usage limit mid-run, the task didn't do anything wrong. It goes back in line, the activity feed says it's paused, and it runs again after the limit resets. If an agent keeps reporting a limit for the same task three times in a row, Atrium stops retrying and asks me, so a misread limit can't loop forever.

Overnight mode

A Mac that goes to sleep runs nothing. So there's a switch in the sidebar: Overnight mode.

With it on, Atrium keeps the Mac awake, but only while it's plugged in and there's work in the queue. It does that by running macOS's own caffeinate tool, tied to the engine's process, so if the engine ever crashes the Mac is free to sleep again. When the queue empties, the Mac sleeps as usual. A queue that's only waiting for a usage limit to reset still counts as work, so the Mac is awake when the limit lifts.

That's the pattern I use most: queue up a few heavy tasks in the evening, plug in, turn on overnight mode, go to bed.

Coming back

Finished work doesn't scroll by in a chat log. It collects in Needs you, one card per result, each with its actions right on it. The Mac app shows the count on its Dock icon and sends notifications as results arrive, titled by what happened: “Ready for review”, “Partly done”, “Couldn't do this”, “Blocked” or “Didn't finish”.

The top of the dashboard and the terminal app greet me with what happened while I was gone: how many tasks finished across how many spaces, how many ended without finishing, and how many couldn't be done, with a nudge to open them and see why. If nothing ran, it says that too: “Nothing ran since you were last here.”

Every card opens to the full detail: the agent's summary, the complete transcript of the run, the files it changed and when. I don't need to have watched it happen to know what happened.

Why this beats babysitting a tab

Watching a model stream feels productive, but it's mostly waiting. A queue turns that waiting into time I get back. The trade is that I can't steer mid-run, so the design leans on two things instead: the task has to be clear up front, and nothing the agent does takes effect until I've looked at it. If a run goes wrong, I find out from its card, I send it back with a note, and it runs again.

A chat tab needs me there while it works. A queue only needs me at the end, for the part that actually needs a person: the yes.
