Tokens, explained simply.

Everything about what an AI agent costs, and how fast it goes, comes down to tokens. This is the mental model I wish I'd had from the start.

NP Nakul Patel / October 29, 2026 / 4 min read

I've been leaning on coding agents a lot this month, and the bills kept surprising me. Some sessions that felt short used far more than I expected. Some long ones were cheaper than I feared.

So I sat down and worked out where the tokens actually go. None of this is secret, but nobody explained it to me in one place, so here it is.

What a token is

A token is the unit of text a model reads and writes: usually a short word, or a piece of a longer one. In English a token averages about four characters, so 1,000 tokens is roughly 750 words.

Code usually takes more tokens per line than prose. Brackets, symbols and indentation all count, and names like fetchData get split into pieces.

Tokens come in two kinds. Input tokens are what the model reads: the system instructions, the conversation, file contents, the results of the tools it ran. Output tokens are what it writes.

Output costs more per token, about five times more on the Claude models I use. But input is where nearly all the volume is, and that's the part that surprised me.

Every step reads everything again

An agent is a model that works in a loop: it reads, decides on an action like opening a file or running a command, sees the result, and goes again. Each trip around that loop is a step.

Here's the catch. The model has no memory between steps. Every time it takes one, the entire conversation so far is sent again as input. Step one reads the instructions. Step two reads the instructions plus step one. Step fifty reads everything.

If every step adds about the same amount of text, the total input over n steps is 1 + 2 + … + n, which grows with n². Double the length of a session and it reads roughly four times as much. That's the main cost of a long agent session, far more than anything the model writes.

This is why “it only made a few small edits” can still be expensive. If it opened forty files and ran the tests six times on the way there, all of that stayed in the conversation and got read again on every step after.

The prompt cache

What makes this bearable is caching.

In plain terms

A prompt cache keeps the processed beginning of a request around for a few minutes. If the next request starts with exactly the same text, that part is read from the cache instead of being processed again. On Claude, a cache read costs about a tenth of a normal input token.

Since each agent step is the previous step plus a bit more, most of every request is a cache hit. That's the hatched part of the diagram.

There are two catches.

  • It only matches an identical beginning. Change anything early in the context, like the instructions or the list of tools, and everything after it is a miss.
  • It expires when idle. About five minutes by default. A session that sits while I'm at lunch pays full price to warm back up.

Cheaper isn't smaller

Caching makes long sessions cheaper. It doesn't make them smaller, and that's a separate problem.

A model only knows what's in its context window: all the text it can see at once. On the models I use it holds hundreds of thousands of tokens. A cached token still takes up room in that window. And a window full of old test output and files the agent opened an hour ago is a window where the requirement I wrote at the start has to compete for attention.

When the window does fill, the tool summarizes older parts to make room. Summaries lose things. An exact requirement becomes “user wants X”, and the edge cases quietly drop out.

The cache is about money. The window is about attention. A long session can be cheap and still be confused.

A few rules of thumb fall out of this:

  1. Short sessions beat long ones.

    Input grows with the square of the length. Two half-length sessions read about half as much as one long one.

  2. Leave the start of the context alone.

    Editing the instructions or swapping tools halfway through throws away the cache for everything after them.

  3. Put reference material in files.

    An agent that reads a file only when it needs it carries less than one that was handed everything up front.

  4. Write down what matters.

    If a decision has to survive a summary, it belongs in a file the agent can reread, not only in the chat.

I've started planning a bigger project around these rules: splitting work across several agents so each one has a small, focused context instead of one agent carrying everything. More on that once it exists.
