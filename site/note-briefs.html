Writing a brief an agent can't misread.

A fresh agent starts with nothing but the brief I hand it. Most bad agent runs I've had came from a vague brief, not a weak model.

NP Nakul Patel / November 6, 2026 / 5 min read

Atrium is built by a handful of agents with separate jobs: one builds, a fresh one reviews, another fixes. I wrote about that split in Why one agent isn't enough. What I didn't say is that the split only works if each agent is told the right things.

In plain terms

A subagent is a fresh agent session started by a main session. It begins with an empty context, the text a model can see at once, and reads only its brief: the written instructions it's handed. It works on its own and sends back a report.

The brief is the only context it has. Anything I know and didn't write down, it doesn't know. So this note is about two questions: when to hand work off at all, and what goes in the brief when I do.

When delegating is worth it

Delegation has a fixed cost, and it's easy to forget. Before a subagent does any work, it costs a brief someone has to write, a handoff where detail gets lost in both directions, and a context it has to rebuild by reading files the main session may already have read.

For a big, separable job that overhead is small next to the work. For a small job it's most of the cost. A few habits follow from that.

Do small lookups yourself

If I already know which file holds the answer, the main session just reads it. Starting an agent to find one function costs more than reading the function.

Batch same-shape edits

Renaming something across thirty files, or updating the wording on every screen, is one brief and one context for one agent. Thirty small agents would each pay the setup cost for a two-line change.

Match the model to the job

Mechanical work, like moving code, applying a pattern that's already decided or writing test fixtures, goes to cheaper, faster models. Plans, architecture and reviews get the strongest model I have. A wrong plan is the most expensive mistake in the pipeline, because everything after it inherits it.

The seven parts of a brief

When I do delegate, every brief now has the same seven parts. Here's the shape, filled in for a review like the one the Money feature got today.

Goal and scope

One sentence for what “done” means, and one for where the edges are. Scope is the part people skip, and it's the part agents need most. Without it, a reviewer asked to check a branch will happily review the whole repo and bill me for it.

What's already ruled out

If I've already decided something, the brief says so. Otherwise a fresh agent will rediscover the same trade-off and propose the option I rejected yesterday, with a confident paragraph about why. Saying “this is decided, check that it holds” turns a debate into a test.

Files to read, not history

A brief that says “read the plan in docs/plans and CLAUDE.md” is short, exact and always current. Pasting the last hour of conversation into a brief carries along every false start with the decisions. If something matters, it belongs in a file the agent can read.

Exact values

Vague words get filled in with guesses. “Use a different port” could mean anything. “Never 7420” can't be misread. Plan 4's reviewer got ports 7450 to 7459, and plan 6's got 7480 to 7489, so two reviews running overnight couldn't collide. The same goes for branch names, commit ranges, folder paths and test commands like bun test ./tests/engine.

Rules

The three rules from my pipeline go in every brief, word for word: no merge or push, no live data, no subagents. They're written as rules, not hopes. They're also backed by things the agent can't talk its way around, like running with ATRIUM_HOME pointed at a temporary folder so my real database isn't even in reach.

A report file

The last line says exactly where the result goes. Not “report back”, but a path. The Money review's file starts with what it reviewed, then its verdict and counts, then each finding with where it is (file and line), how it happens and the fix.

A file beats a chat reply for three reasons. It survives when my main session's context gets summarized. I can read it without scrolling. And the next agent, the one fixing the findings, can be told to read it, which is far more exact than me retelling it.

That review also left 12 small tests in its scratchpad, one per finding plus a control. Eleven failed on the branch as it was, and the control passed. That's the kind of report I want: not “I think this leaks”, but a test that shows it does.

Keep a ledger

Briefs are for subagents. The main session needs its own memory too.

A long session eventually gets summarized when its context fills up, and the summary forgets things. So my main session keeps a plain markdown ledger in the repo: what's done, what's running, which worktree and branch, what's next and why. Each ruling gets one line, with what it costs if it turns out wrong.

The ledger from Wednesday night ran through four plans while I slept, with a usage limit in the middle. After the limit reset, the session reread the ledger and picked up where it left off. The ledger costs a few hundred tokens to keep current, and it's what lets a long session survive its own memory loss.

A brief is the agent's whole world. If it isn't written down, it doesn't exist.
